Title: TSManagement — Architecture & Project Overview

**Overview:**

Purpose: Timesheet system with a .NET backend, Angular frontend, and tests + coverage reports.
Solution file: TSManagement.sln

**Architecture (high-level):**

Layered flow: Client (Angular) -> HTTP API (Timesheet.API) -> Application services (Timesheet.Application) -> Domain (Timesheet.Domain) -> Persistence (Timesheet.Infrastructure / EF Core) -> Database (script.sql).
Data flow: Controllers accept requests -> call Application services -> services manipulate Domain entities and use TimesheetDbContext -> EF Core maps entities to DB. Responses use DTOs mapped by AutoMapper.

**Design patterns & practices:**

Layered/Clean-inspired architecture: separation of concerns between API, application logic, domain, and infrastructure.
Dependency Injection: built-in .NET DI configured in Program.cs.
DTO + Mapping: DTOs in DTOs mapped via MappingProfile.cs to Domain entities.
Service layer: Timesheet.Application/Services/* implements business use-cases and orchestrates repositories/DbContext.
EF Core (DbContext as repository): Timesheet.Infrastructure/TimesheetDbContext .cs used directly by services .
Reactive frontend: Angular + RxJS for async flows; NgRx used for project-related state (actions/reducers/effects).
Testing: Unit tests in Timesheet.Test (service/controller tests) and frontend unit tests in angular-login-app (Angular test suites). Test results and coverage appear under TestResult.

**Project structure (concise):**

Timesheet.API — ASP.NET Core Web API (controllers, routing, DI bootstrap: Program.cs).
Timesheet.Application — service layer, DTOs, AutoMapper mapping.
Timesheet.Domain — domain entities and enums.
Timesheet.Infrastructure — EF Core DbContext, migrations, persistence concerns.
Timesheet.Test — .NET unit tests for services/controllers; uses in-memory DB for some tests.
angular-login-app — Angular frontend: components, services, store, tests, package.json scripts.
script.sql — database schema / seed scripts.
TestResult — test run artifacts and coverage reports.

**Key features:**

Timesheet CRUD (entries, hours, approvals) via API and frontend UI.
Manager workflows: project codes CRUD, project assignments, approve/reject timesheets.
Reporting: employee/project/week/billable reports generated by ReportService.
Frontend UX: week navigator, draft saving, optimistic UI for responsive updates.

**Trade-offs & rationale:**

AutoMapper for DTO mapping
Pro: Reduces mapping code and repetitive conversions.
Con: Hidden mapping rules can make debugging mapping issues harder; add mapping unit tests.
NgRx used selectively (projects state)
Pro: Predictable state management and good DevTools for complex state.
Con: Adds cognitive overhead; may be overkill for small slices — consider service-based caching for simple data.
Client-side drafts & optimistic updates
Pro: Better UX and offline resilience.
Con: Must implement robust reconciliation and error handling to avoid data divergence.

**Run & dev notes:**

Backend (API): open solution and run Timesheet.API from Visual Studio or via CLI:
dotnet build then dotnet run --project Timesheet.API
Frontend (Angular): from angular-login-app:
Ensure the frontend environment config or proxy points to the running API base URL.
Database: run script.sql or apply EF Core migrations in Migrations.

**Tests & reports:**

.NET tests: run dotnet test for Timesheet.Test (CI should pick up TestResult/*.trx).
Frontend tests: npm run test in angular-login-app.
Coverage artifacts: see TestResult (cobertura XMLs and TRX files) for CI integration.

**Where to look first (key files):**

Program.cs — API bootstrap and DI registrations.
Controllers — controller entry points.
Services — business logic.
MappingProfile.cs — AutoMapper profiles.
Timesheet.Infrastructure/TimesheetDbContext .cs — EF Core mappings and DbSets.
app — Angular components and app.config.ts for DI and store.
Timesheet.Test and TestResult — tests and reports.
